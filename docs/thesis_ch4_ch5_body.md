# 第 4 章 布局引擎与自绘分页编辑器的设计与实现

> 本章正文对应提纲 v2（`docs/thesis_ch4_ch5_outline.md`）。全文以 NewWord 实际代码为准，涉及的关键类：`Engine::DocumentModel`、`Engine::QTextAdapter`、`Engine::LayoutEngine`、`Engine::DocxExporter`、`PagedEditorWidget`、`PagedDocumentLayout`、`PagedImageObject`、`PagedFloatingBoxes`。

---

## 4.1 问题与目标

### 4.1.1 问题背景

现代办公套件的功能膨胀使得"打开即写、写完即走"这一基本诉求被边缘化：插件、云同步、遥测与 COM 基础设施将启动时间拖至数秒。NewWord 的目标是构建一个 macOS 轻量文字处理器，强调**启动快、编辑跟手、保存可靠**。为了在"编辑体验"与"页面呈现"两个维度都达到可用水平，本文没有直接选用完整的 Word 级 WYSIWYG 路线，而是围绕一个核心矛盾展开研究：**编辑视图与打印/预览视图如何共享同一套排版语义，避免页数分叉**。

### 4.1.2 双路径分页问题

Qt 的 `QTextEdit` 天然把文档当作连续流处理：一旦设置 `pageSize` 高度为 −1，重排便会把全部内容摊成一列。若在此之上再对预览/PDF 采用独立的"几何估算"（用 `QTextDocument::size()` 除以内容框高度得出页数），两种口径会随文档复杂度增长而分叉——长文、含图、多页表场景下几何估算的误差可达数页（见 5.5 节实测）。

因此，本设计的起点是：**让"页"成为系统中一等公民**。最终形成了"引擎 + 自绘分页编辑器"双路径：由 `LayoutEngine` 统一负责预览/PDF/导出的分页与绕排；由自绘控件 `PagedEditorWidget` 负责编辑视图的真实分页。两条路径的断行均出自同一套 Qt 排版，行边界基本一致，页数口径各自明确。

### 4.1.3 目标演进与阶段划分

系统按五个阶段逐步构建，每阶段都有独立的可验证成果：

| 阶段 | 内容 | 成果 |
|------|------|------|
| 0 | `DocumentModel`：布局与导出的规范视图 | 块/段/Run 语义模型 |
| 1 | `LayoutEngine` → 预览 / PDF | 引擎分页、绕排 |
| 1+ | 活页页数与引擎对齐（早期方案） | 引擎断点驱动 `QTextEdit` 页缝——**假分页，最终放弃** |
| 2 | `Model → DocxExporter` | 内置 DOCX 保存 |
| 3 | **自绘分页编辑器**（本设计核心） | 编辑视图本身即为真实分页，引擎回归"预览/PDF/导出" |

阶段 1+ 的"假分页"方案曾尝试用引擎的断点位置给 `QTextEdit` 画页缝，实践后发现两个不可接受的缺陷：

1. **观感突变**：`QTextEdit` 内部按连续流排版，页缝只是"画上去的分隔线"，文字与页脚、上下页内容可能重叠，滚动与选中行为也不符合真实分页直觉；
2. **两套布局无法收敛**：编辑视图用 Qt 排版、导出/预览用引擎排版，即便页数对齐，行边界差异也无法通过"画缝"抹平，只能靠事后修正，且修正逻辑与日俱增。

这一失败成为阶段 3 的直接动机：**与其在错误的视图之上叠加分页，不如让编辑视图本身真实分页。**

### 4.1.4 本章目标

- 给出双路径的总体架构与数据流（4.2）；
- 阐述 `DocumentModel` 与 `QTextAdapter` 的建模取舍（4.3、4.4）；
- 阐述 `LayoutEngine` 的分页与绕排算法（4.5、4.6）；
- 详细论述自绘分页编辑器的设计难点与解法（4.7）；
- 论述**增量分页**这一性能关键机制（4.8）；
- 说明 Model → DOCX 的导出路径（4.9）。

## 4.2 总体架构

### 4.2.1 系统组成

NewWord 的分页相关组件结构如下：

```text
QTextDocument ──分页页尺寸 = 页面内容框──► PagedEditorWidget（自绘分页编辑：逐页裁剪绘制 / hitTest / IME / 选区）
        │
        └─ QTextAdapter → DocumentModel
                             ├─ LayoutEngine → 预览 / PDF / 导出分页与绕排
                             ├─ DocxExporter → 内置 DOCX 保存（阶段 2）
                             └─ DocxImporter ← 内置 DOCX 打开（适配层）
```

### 4.2.2 关键取舍

- **数据流单向**：编辑缓冲始终是 `QTextDocument`；`DocumentModel` 是布局与导出的规范视图，由 `QTextAdapter` 从 `QTextDocument` 转换得到，不允许反向写回。
- **编辑器分页以 `QTextDocument` 为准**：`PagedEditorWidget` 将 `QTextDocument::setPageSize` 设置为"内容框宽 × 内容框高"，让 Qt 文档自身真实分页；控件逐页裁剪绘制，用 `hitTest` 定位光标。编辑器不依赖引擎的页数。
- **引擎只管预览/PDF/导出**：`LayoutEngine` 消费 `DocumentModel`，输出 `LayoutPage` 列表。
- **断行同源**：编辑器的 `QTextLayout` 与引擎的 `QTextLayout` 均为 Qt 排版产物，因此行边界基本一致；复杂文档（多页表、绕排、脚注）允许细微差别，本文在 5.5 节如实交代边界，不做"完全 WYSIWYG"的过度声明。

## 4.3 文档模型 DocumentModel

### 4.3.1 设计目标

`DocumentModel` 是布局与导出的**规范视图**。它刻意不做成完整的 Word DOM——只保留排版与持久化所需的语义，避免过早引入样式集、母版、域等重量级概念。

### 4.3.2 层次结构

模型自顶向下分为三层：

1. **节（`DocSection`）**：携带自己的页面设置（纸张/页边距/页眉页脚距离），一个文档可有多个节；
2. **块（`DocBlock`）**：段落（`DocParagraph`）或表格（`DocTable`），每种块记录 `documentPosition`（在 `QTextDocument` 中的字符偏移），作为分页锚点与导出定位的依据；
3. **段落内 Run（`DocRun`）**：一段连续同格式的文本，或一个原子对象（图片/公式）。Run 携带 `CharStyle`（字体、粗斜下划线、前景/背景色、上下标），原子对象携带尺寸与图片数据。

```cpp
struct DocRun {
    QString text;
    CharStyle style;
    bool isAtomic = false;      //!< 非文本原子（图片/公式）
    qreal atomicWidthPt = 0;
    qreal atomicHeightPt = 0;
    QImage image;
    int imageWrap = 1;          //!< 0=inline 1=block 2=floatLeft 3=floatRight
    int imageAlign = ...;
    QString footnoteId;         //!< 脚注引用标记
    QString endnoteId;          //!< 尾注引用标记
    QString commentId;          //!< 批注区间标记
};
```

### 4.3.3 表格建模

表格采用**完整网格**建模：`DocTable.rows` 为 `[row][col]` 的二维数组，含 `columnSpan`/`rowSpan`/`covered` 三要素。其中 `covered=true` 表示该格被其他单元格的合并所占据（本身无内容），这一表示在引擎分页（4.5.3）与 DOCX 导出（4.9.3）中都被直接复用，避免在两条路径里各写一套合并展开逻辑。

### 4.3.4 附注结构

脚注/尾注/批注采用"**正文标记 + 内容表**"分离的建模：正文 Run 只携带 `footnoteId` 这类引用标记，正文内容存放在 `DocumentModel::footnoteBodies` / `endnoteBodies` / `comments` 哈希表中，另以 `footnoteOrder` 等有序列表维护文档出现顺序。这样正文排版不必感知附注体，附注在引擎层独立布局（见 4.5.4）。

## 4.4 适配层 QTextAdapter

### 4.4.1 职责

`QTextAdapter` 完成 `QTextDocument` → `DocumentModel` 的单向转换，覆盖三类内容：字符格式（颜色、粗斜下划线）、图片资源（转换为 `DocRun::image` 原子）、表格（含合并单元格）。它保证了"编辑缓冲"与"规范视图"之间的一致性由构造期一次转换保证，后续布局/导出不再读取 `QTextDocument`。

### 4.4.2 导入不对称

需要说明的是，本文的 DOCX **导入**路径并未对称为 `DocxImporter → DocumentModel → Qt`，而是仍走桥接（mammoth）/ `DocxIO::load` 直接进 `QTextDocument`。这是有意的取舍：编辑视图的规范数据源是 `QTextDocument`，导入直接落到该数据源可避免二次转换的开销与语义损耗；导出阶段则完整走 `DocumentModel`（见 4.9）。这一不对称在 5.7 节作为已知局限如实交代。

## 4.5 分页引擎 LayoutEngine

### 4.5.1 断行

引擎断行直接使用 `QTextLayout`，与 Qt 编辑器共享同一套文本度量与断行规则，这是"编辑/导出行边界基本一致"的根本保证。段落排版时，先按 Run 构建文本与 `FormatRange` 列表，再交给 `QTextLayout` 逐行切分；每行输出为 `LayoutLine`（携带行内格式、宽度、ascender）。

### 4.5.2 分页基本规则

`LayoutEngine::layout` 以**内容框**（`contentRectPoints`：页面尺寸减去四边距与页眉页脚距离）为排版范围，按以下规则切页：

- 正文块自上而下累积高度 `y`，当 `y + 下一行高 > 可用高` 时切页；
- **表以行为原子**：一行（含其合并跨行的高度）整体决定归属，不做单元格内拆分；
- **图为原子块**：图比剩余空间高时整体移到下一页；图高于整页时等比缩放以落入内容框；
- 输出 `LayoutPage` 列表，每页记录 `startDocPos`（该页首行对应的文档偏移），用于页缝定位与"文档偏移 → 页"的映射。

### 4.5.3 绕排

引擎支持图片的四周型绕排（`imageWrap` 为 `floatLeft`/`floatRight`）：浮动图被放于行首后，记录其占用的高度区间 `wrapBottomY` 与收缩后的文字宽度 `wrapTextW`，后续段落行在该区间内按收缩宽度排版，越过区间后恢复整行宽。绕排区间是**页面局部**的——切页时丢弃残余高度，避免上一页的浮动图高度泄漏到下一页。

### 4.5.4 脚注与尾注布局

脚注在引擎中按"页脚预留"方式实现：行切分时若该行包含脚注标记，则先为对应脚注测量高度并预留底部空间；当行放不下时，采用**快照-回滚-重试**策略——先保存当前已预留的脚注集合，若行溢出则回滚预留、切页、在新页重新预留，保证"行、正文、脚注三者归属一致"：

```cpp
// 行级切页：脚注预留与正文切页原子化
const LayoutSession::Snapshot beforeNotes = session->snapshot();
session->claimInRange(markers, line.textStart(), line.textLength());
if (*y + h > session->usableHeight() && *y > 0.01) {
    session->restore(beforeNotes);          // 回滚本行脚注预留
    flushPage(session, pages, page, pageIndex, y);  // 切页
    session->claimInRange(markers, ...);    // 在新页重新预留
}
```

尾注则作为独立章节在文档末尾新起一页统一排布，按尾注出现顺序编号。

### 4.5.5 引擎边界

引擎明确不做：复杂表跨页（单元格纵向拆分）、分栏、脚注在 Word 级样式中的完整语义、域自动更新。这些边界在 README 与 5.7 节均有声明，属于"够用而非完备"的设计范围。

## 4.6 绘制与接线（预览 / PDF）

### 4.6.1 绘制组件

预览与 PDF 由 `LayoutPainter` / `PageDocumentPainter` 消费 `LayoutPage` 绘制：正文按 `LayoutLine` 逐行绘制（应用行内格式），表格按行绘制边框与单元格，页眉页脚与页码按同一份 `HeaderFooterSettings` 绘制在每页。因此**预览、PDF、打印三种出口共享同一绘制代码**，不存在"预览一套、打印另一套"的分叉。

### 4.6.2 与编辑器的关系

预览/PDF 的页数由引擎决定；编辑器页数由 `QTextDocument` 决定。两者断行同源，行边界基本一致；但编辑器打字期间的页码为估算值（增量分页特性，见 4.8），停顿 120ms 后补齐精确页数。本文在 5.5 节用数据说明：这一口径差异是**有意的设计**，而非缺陷。

## 4.7 自绘分页编辑器（核心）

### 4.7.1 为什么 QTextEdit 不可行

`QTextEdit` 强制文档连续流：在实现阶段 3 前，先做了一个小型实验——给 `QTextDocument` 设置分页页高后，通过 `QTextEdit` 打开并触发一次重排，`documentLayout()->documentSize()` 立即返回整篇连续高度，页面设置被覆盖。这一现象的根本原因是 `QTextEdit` 的 viewport 逻辑要求文档"摊平"以支持其自身的滚动与绘制模型，任何分页意图都无法在既有控件上实现。

结论：**要真实分页，必须放弃 `QTextEdit`，自行实现一个拥有编辑语义的分页控件。**

### 4.7.2 总体设计

`PagedEditorWidget`（继承 `QWidget`）自绘实现以下能力：

| 能力 | 实现方式 |
|------|----------|
| 真实分页 | `QTextDocument::setPageSize = 内容框宽 × 内容框高`；`PagedDocumentLayout` 维护页区间 |
| 逐页绘制 | `paintEvent` 中按可见页裁剪绘制，只画屏幕内页面，非可见页不进入绘制路径 |
| 光标定位 | `documentLayout()->hitTest` 将鼠标位置映射为文档偏移 |
| 选区/剪贴板 | 控件自行管理 `QTextCursor` 选区与 `QClipboard` 读写 |
| 输入法 | 重写 `inputMethodEvent` / `inputMethodQuery`，在分页坐标系中返回光标矩形，支持中文等 IME 组合输入 |
| 滚动 | 自绘垂直滚动条，滚动值由"页索引 + 页内偏移"换算 |

### 4.7.3 难点一：Qt 的断页怪癖

实验发现 Qt 文档布局存在一个反直觉行为：**放不下的最后一行会被放置在恰好等于页高的位置，下一页从"页高 + 该行高"开始**。也就是说，Qt 并不会把溢出行裁到下一页，而是把它顶在页边界上，导致页面高度虚增。

解法：`PagedDocumentLayout` 用"**缩减布局页高**"消除该行为——布局页高取 `内容高 − 最大行高 − 1px`，使得原本"顶到页底"的行落在内容框内部：

```cpp
// 找出全文最大行高，作为布局页高的缩减量
for (QTextBlock b = m_document->begin(); b.isValid(); b = b.next()) {
    const QTextLayout *tl = b.layout();
    for (int i = 0; i < tl->lineCount(); ++i)
        maxLineHeight = qMax(maxLineHeight, tl->lineAt(i).height());
}
m_layoutPageHeight = qMax(120.0, m_contentHeight - maxLineHeight - 1.0);
m_document->setPageSize(QSizeF(m_contentWidth, m_layoutPageHeight));
```

由于 Qt 用"页高 + 行高"从页边界起排下一页，缩减后的布局页高保证**任何行都不会穿越页框**。随后 `PagedDocumentLayout` 遍历每块每行，用 `块顶 + 行内偏移` 得到每行的真实文档 Y 坐标，按 `floor(top / 布局页高)` 归入页，再聚合成每页的 `PageRange{minTop, maxBottom}` 作为"文档 Y → 页"的映射。

### 4.7.4 难点二：跨页块与边界 off-by-one

增量重建（见 4.8）中，一个块可能横跨两页，导致"从编辑页开始遍历"时首行落在上一页。`PagedDocumentLayout::ensureRangesThroughPage` 对这类边界做了处理：当发现遍历到的第一个行落在 `page−1`（预期前一页）时，**回退一页**重新从该行聚合并重建上一页的 end；同时，若某页在重建后为空或内容发生了大幅前移（如大段删除），则安全地回退到全量 `recompute()`。这套"回退重排 + 全量兜底"策略使增量路径的覆盖率接近朴素方案，同时避免了误触全量的性能回退。

### 4.7.5 难点三：大图性能

含大量图片的文档（如扫描件）在绘制时若对每帧重新缩放原图，开销不可接受。`PagedImageObject`（`QTextObjectInterface` 实现）维护一个以"显示尺寸"为键的 `QPixmap` 像素图缓存：每张图**每种目标尺寸只缩放一次**，之后直接 blit；文档加载时同时做资源降采样（最长边 ≤ 2048px），从源头控制内存与缩放成本。实测整页重绘由 280ms 降至 2.9ms（见 5.4 节）。

### 4.7.6 编辑交互

- **浮动文本框**：`PagedFloatingBoxes` 维护绝对定位文本框（每页可放置、拖动、缩放、双击进入行内编辑），编辑结果写回对应页；
- **表格列宽拖动**：命中测试列边框后进入拖动会话，按列宽占比实时调整并重排；
- **网格线**：页面视图下可显示 5mm 辅助网格（仅辅助定位，不参与排版）；
- **拖放**：支持把本地图片拖入文档插入为原子图。

## 4.8 增量分页（性能关键）

### 4.8.1 朴素方案的代价

若每次按键都"全文重排 + 全量遍历算页区间"，编辑成本与文档长度成正比。实测（见 5.3 节前的探针数据）：80 万字文档在**每次按键全量分页**时约为 **511ms/键**——在输入场景完全不可用。因此分页必须增量。

### 4.8.2 设计

`PagedDocumentLayout` 将"编辑影响面"压缩到最小：

1. **`markDirty(position)`**：编辑发生后只记录"首个受影响块序号"（`m_rebuildBlock`），并把该块所在页之后的区间标记为过期；编辑点之前的页区间保持缓存有效。
2. **`ensureRangesThroughPage(pageIndex)`**：绘制或查询页 N 时，只从 `m_rebuildBlock` 开始向后遍历块，重建受影响页的 `PageRange`，**复用未改动前缀**；若遍历提前越过了请求页，则记录"下次从该块继续"，实现真正的按需延迟重建。
3. **空闲全量补齐**：控件用 120ms 防抖定时器在停止输入后执行一次全量 `recompute()`，补齐精确页数与滚动条范围；另用 40ms 判定窗区分"真格式变更"与普通编辑，避免无谓重排。

这套机制带来的观感是：**打字期间页面只局部重建（跟手不卡顿），停顿后页码从估算自动收敛为精确**——与 Word 的延迟分页行为一致。

### 4.8.3 编辑路径上的两个 QTextDocument 病理

开发中还实测出两个 Qt 层面的 O(n) 病理并给出对策（均有基准探针支撑，见 5.3 节）：

1. **HTML 导入的巨长单段落**：`setHtml` 产生的大量隐式格式碎片使后续编辑退化为 O(n)。对策：`PagedEditorWidget::normalizeDocumentStructure` 用 cursor API 重建文档结构，恢复快速编辑路径。
2. **全量排版后的插入开销**：`documentSize()` 触发全文排版后，任何插入都要重排受影响区域。对策：增量分页 + 按需查询（只在绘制/查询页时触发该页的布局），避免一次性全文排版。

---

## 4.9 阶段 2：Model → DOCX

### 4.9.1 主备路径

DOCX 导出采用"桥接优先、内置兜底"策略：若 Python 桥接（html2docx）可用，则优先使用增强引擎；否则回退到内置 `DocxExporter`（`DocumentModel` → OOXML）。桥接失败时状态栏提示，主路径不受影响。

### 4.9.2 内置导出实现

`DocxExporter::save` 从 `DocumentModel` 直接生成 OOXML 包：手写 `[Content_Types].xml`、`_rels/.rels`、`word/document.xml`、`word/_rels/document.xml.rels`、`styles.xml`，并支持：

- 段落/Run 级格式：字体、字号、粗斜下划线、颜色、底纹、上下标；
- 图片：`wp:inline` + `pic:pic` 绘制，`word/media/*.png` 打包，关系文件正确登记 `rId`；
- 表格：`w:tblGrid` 列宽、`w:gridSpan` 横向合并、`w:vMerge` 纵向合并、`w:shd` 底纹、行高；
- 页眉页脚：`header1.xml`/`footer1.xml` + `w:headerReference`/`w:footerReference`，页码用 `PAGE` 域；
- 脚注/尾注/批注：`footnotes.xml`/`endnotes.xml`/`comments.xml` + 正文 `footnoteReference`/`commentRangeStart|End` 标记。

### 4.9.3 合并单元格的双路径一致性

引擎分页（4.5.3）与 DOCX 导出（4.9.2）都直接消费 `DocTable` 的 `covered`/`columnSpan`/`rowSpan` 网格表示：引擎在切页时把跨行块整体上移，导出时把 `covered` 格转为 `w:vMerge continue`。两条路径共用同一建模，避免了"分页是一种合并语义、导出是另一种合并语义"的分叉。

---

## 4.10 本章小结

本章完成了两条相互独立又同源的路径：

1. **引擎路径**（阶段 0/1/2）：`DocumentModel` → `LayoutEngine` → 预览/PDF/导出，提供统一的分页、绕排与持久化；合并单元格、脚注/尾注/批注等高级语义均在此建模。
2. **编辑器路径**（阶段 3）：`PagedEditorWidget` 放弃 `QTextEdit`，以 `QTextDocument` 真实分页为基础自绘实现完整编辑语义；`PagedDocumentLayout` 用"缩减布局页高 + 页区间 + 增量重建"解决 Qt 断页怪癖并实现增量分页；`PagedImageObject` 用像素图缓存解决大图绘制性能。

两条路径的关键机制与性能表现，将在第 5 章以可复现的基准与测试数据加以验证。阶段 3 从 v1 提纲中的"非目标"转变为全文的核心贡献，叙事闭环成立。

# 第 5 章 实验评测与结果分析

## 5.1 评测目的

本章围绕三个问题展开评测：

1. **性能**：自绘分页编辑器在"打开 / 逐键编辑 / 整页重绘"三方面的大文档表现如何？增量分页是否真正把编辑从 O(n) 拖回可用区间？
2. **正确性**：跨页打字、页边界、文本框/公式/表格等编辑交互是否保持不变量？（52 个用例 + 初始化/清理，共 56 个测试槽）
3. **一致性**：预览/PDF 由引擎统一分页、编辑器断行同源，页数口径是否明确？阶段 1 的"活页 vs 引擎"一致性结论是否仍成立？

## 5.2 性能评测方法

### 5.2.1 工具与条件

- 基准工具：`NewWordBenchEditorPerf`（自绘编辑器真实组件路径，offscreen 渲染）、`NewWordBenchMixedDoc`（编辑缓冲 `QTextDocument` 的原始编辑成本基线）；
- 环境：Qt 6.11、macOS、**Debug 构建**（Release 会更快）、`QT_QPA_PLATFORM=offscreen`，可在本机复现；
- 指标：打开耗时（`setHtml` + 首次分页）、尾部逐键、**中部逐键**（最坏位置，编辑点之后的全文重排成本全部计入）、表格内逐键、整页重绘。

### 5.2.2 探针

基准工具还内置了若干探针用于定位瓶颈：`plain/html/normalized` 三种文档结构的碎片数量对比、编辑后布局查询的耗时、规范化前后逐键插入耗时等，这些探针直接支撑 4.8.3 的两个病理结论。

## 5.3 性能结果（基准表）

| 文档 | 打开 | 尾部逐键 | **中部逐键** | 表格内逐键 | 整页重绘 |
|------|-----:|--------:|-----------:|----------:|--------:|
| 200k 字符（≈126 页）纯文本 | 145ms | 0.03ms | **1.6ms** | — | — |
| 200k 字符 + 200 图 + 200 表 + 1.5 万格式碎片 | 328ms | 2.1ms | **69ms** | 127ms | — |
| 800k 字符（≈500 页）纯文本 | 595ms | 0.07ms | **6.8ms** | — | — |
| 800k 字符 + 1112 张大图（≈1670 页） | 852ms | 0.20ms | **22ms** | — | **2.9ms** |

**分析**：

- **打开**：80 万字 + 千余张大图在 852ms 内完成"导入 + 首次分页"，与文档规模接近线性，无超线性退化；
- **纯文本**：80 万字中部逐键 6.8ms、尾部逐键 0.07ms，均在 60fps 预算（约 16ms）内——增量分页使"最坏位置编辑"从 511ms 降到可用区间；
- **混合文档**：中部逐键 69ms 是编辑缓冲（`QTextDocument`）的固有边界——大量表格与碎片化格式导致编辑失效范围扩大，这属于**架构边界而非控件缺陷**，也是后续自研编辑缓冲（Rope + 增量排版）的动机（见 5.8）；
- **整页重绘**：含大图页面重绘 2.9ms，像素图缓存生效。

## 5.4 优化前后对比（核心证据）

| 优化项 | 优化前 | 优化后 | 提升 |
|--------|-------:|-------:|------|
| 80 万字**中部逐键** | 509ms（每键全量分页） | **6.8ms**（增量 + 空闲补齐） | ≈ 75× |
| 80 万字尾部逐键 | 511ms | **0.07ms** | ≈ 7300× |
| 整页重绘（大图页） | 280ms（逐帧缩放原图） | **2.9ms**（像素图缓存 + 降采样） | ≈ 96× |
| 全量分页触发时机 | 每次按键 | 空闲 120ms 防抖 | 打字不阻塞 |

优化构成的文字解释：**全文重排（O(n)，每键）→ 按需区间重建（只重排受影响页）→ 空闲全量补齐（停止输入后收敛页码）**，三层递进把"编辑成本"从"与文档长度成正比"压缩为"与局部改动成正比"。所有数据均由同一基准工具在每次优化后复测，保证可复现。

## 5.5 一致性验证（阶段 1 成果保留）

阶段 1 建立的三源对比（几何估算 / 活页 / LayoutEngine）结论如下（完整数据见 `docs/pagination_eval.md`，由 `NewWordCoreTests::pagination_writeEvalMarkdown` 生成）：

| 样例 | 几何估算 | 活页(引擎) | LayoutEngine | Δ几何 | Δ活页 |
|------|--------:|----------:|-------------:|------:|------:|
| 空文档 | 1 | 1 | 1 | 0 | 0 |
| 短正文 | 1 | 1 | 1 | 0 | 0 |
| 长纯文本×40 | 3 | 4 | 4 | +1 | 0 |
| 长纯文本×80 | 5 | 8 | 8 | +3 | 0 |
| 标题+正文 | 1 | 1 | 1 | 0 | 0 |
| 含表格 | 1 | 1 | 1 | 0 | 0 |
| 含图×4 | 3 | 4 | 4 | +1 | 0 |
| 多页表×36行 | 3 | 6 | 6 | +3 | 0 |

**结论**：8/8 样例 Δ活页=0（旧方案下活页页数与引擎完全一致）；几何估算在长文/图/表上偏差 1~3 页，论证了"为何不能用几何估算充当页数来源"。需要说明的是，编辑器改版后"活页"已由 `QTextDocument` 真实分页取代，本表作为阶段 1 的独立成果引用，不再用于当前编辑视图；当前"编辑页数（Qt）"与"预览/PDF 页数（引擎）"因断行同源而基本一致，复杂文档允许细微差别——这是诚实的设计边界。

## 5.6 功能与正确性测试

测试按主题拆分，覆盖编辑、布局与持久化：

| 测试套件 | 用例数 | 覆盖内容 |
|----------|-------:|----------|

## 5.7 威胁效度与局限

1. **字体与环境**：评测固定使用 Helvetica 12pt、A4；未覆盖全部中文字体度量差异。不同字体（尤其等宽与衬线混合）下断行与行高可能产生系统偏差。
2. **表格**：引擎不做单元格内拆分，极复杂的 Word 表格不在保证范围。
3. **导入不对称**：DOCX 导入仍为桥接/`DocxIO::load` 直达 `QTextDocument`，未对称成 `DocxImporter ← DocumentModel`；导出侧的 Model 语义在导入侧不完整。
4. **极端负载**：超长单段落、极端大图组合仍是 Qt 排版与内存的上限，已通过规范化重建与资源降采样缓解，但并非彻底消除。
5. **Debug 构建**：基准数据为 Debug（offscreen），Release 与真实 GPU 绘制环境下数值会有差异，论文引用时应注明条件。

## 5.8 本章小结

本章用可复现的基准与测试回答了三个问题：

1. **性能**：自绘分页编辑器 + 增量分页使 80 万字中部逐键从 509ms 降至 6.8ms（≈75×），大图页整页重绘 2.9ms，大文档编辑达到"可用"目标；
2. **正确性**：52 个核心用例 + 4 个标签页用例全部通过，跨页、合并单元格、附注等不变量得到保障；
3. **一致性**：引擎统一负责预览/PDF/导出分页，编辑器断行同源，页数口径明确；阶段 1 的"活页=引擎"结论保留为独立成果。

后续工作包括：编辑缓冲自研（Rope + 增量排版，参考 RWord 方向）以突破混合文档的 O(n) 失效范围、DOCX 导入对称、评测样例扩展（多字体、多纸张）。本章数据与代码路径完整对应，可作为毕设演示（打开 80 万字长文 → 中部连续打字 → 滚动翻页 → 导出 PDF 对照）的量化支撑。
